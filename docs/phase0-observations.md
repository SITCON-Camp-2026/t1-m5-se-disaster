# Phase 0 Observations

## 我們做出了什麼？

- 首頁保留 `原始資訊` 與 `整理工作台` 兩個分頁。
- 原始資訊卡片會顯示查核狀態、草稿狀態、推測地點、工種要求與資料品質提示。
- 整理工作台可以建立、編輯、儲存、重設與清除整理草稿。
- 草稿可編輯候選類型、工種要求、信心程度、下一步、是否不可直接行動、整理依據、卡住的地方與人工修正或質疑。
- 工種要求使用多選清單，儲存在草稿的 `workTypeLabels`。
- 排序可依時間、推測地點、可信度、任務方式 / 下一步、草稿狀態切換。

## 哪些資料讓 agent 很容易整理？

- 有明確時間、地點、來源與數量的資料比較容易整理，例如 M-009、M-010。
- 直接提到物資狀態、剩餘數量、停止收受項目的資料，比較容易做成候選摘要。
- 但即使資料看起來完整，只要 `verificationStatus` 仍是 `needs_review`，畫面仍不能把它顯示成已確認事實。

## 哪些資料讓 agent 亂補或誤判？

- 社群轉錄容易讓 agent 補出原文沒有的來源可信度，例如 M-004、M-007。
- 「有人說」「留言有人說」「截圖寫」這類資訊容易被誤當成直接可用的事實。
- 工種要求目前是關鍵字推測，可能把「不缺鏟子」也推成清淤 / 挖土，因此工種必須能在草稿中人工修正。

## 哪些資訊不能直接變成任務？

- 未查核或待人工確認的資訊都不能直接派工。
- 地點不明、時間不明、需求內容不明確、來源是二手轉述的資訊不能直接變成任務。
- M-008 說「A 區先不要再派人」，但沒有說原因，不能直接推導成任務完成或道路危險。
- M-012 是外地家屬來電，無法確認當事人位置，也不能直接建立救援任務。

## 哪些資訊的操作者不是當事人？

- M-011 是志工代長者轉述，需要確認長者是否同意公開完整地址。
- M-012 是外地家屬來電，不在現場，也不能確認親友目前位置。
- 這類資訊應該標示需要人工確認，不能把來電者或轉述者直接當成當事人。

## 我們剛剛偷偷假設了什麼？

- 推測地點是用原文關鍵字判斷，不代表有確認地址。
- 工種要求是用關鍵字初步推測，不代表已經完成任務分類。
- 可信度排序只是根據 `verificationStatus` 排列，不代表資料真的可用。
- 草稿狀態只存在前端記憶體，重新整理頁面後會回到預設。

## 如果要讓這個工具變可靠，下一步需要什麼？

- 需要更清楚的資料格式，明確分開原文、來源、回報者、當事人、地點、時間、需求、確認狀態。
- 需要人工確認角色與流程，尤其是誰可以把草稿升級成可派工資訊。
- 需要狀態機，避免 `needs_review` 被誤顯示成已確認。
- 若未來要串 AI API，必須經由後端保管 API key，不能把 token 放在前端或 repo。

## 我們需要更清楚資料格式的地方

- 工種要求目前是 `workTypeLabels` 草稿欄位，後續若正式化，需要定義可選值與是否允許多選。
- 推測地點目前不是地址欄位，只是文字線索。
- `evidence` 和 `blockers` 目前是字串陣列，UI 用 checkbox 加其他輸入產生。
- 需要區分 AI 推測、人工修正與已確認資料。

## 我們需要人工確認的地方

- 社群轉錄是否有原始來源。
- 截圖或公告是否仍有效，以及日期是哪一天。
- 地點是否足以派人前往。
- 當事人是否同意公開地址或建立任務。
- 工種要求是否符合現場實際需求。
