# 需求取捨決策

> 這份文件由 Codex 先產生草稿，已加入目前人類取捨。後續仍可在小隊討論後修正。

## 我決定 v1 優先服務的使用者

- [ ] 回報者
- [ ] 資訊整理者
- [x] 行動者

原因：

我決定 v1 先服務行動者，因為目前 prototype 最危險的誤解是：行動者看到醒目的 `工種要求`、`推測地點` 或 `已確認資料` 後，可能以為自己可以直接前往現場。v1 應優先讓行動者分辨「可以準備下一步確認」和「不可直接行動」，而不是讓畫面看起來像派工系統。

## 這個使用者最想完成什麼

- 快速分辨哪些資訊只是原始線索，哪些資訊已經足夠進入下一步確認。
- 看懂自己現在應該先聯絡誰確認、暫時不要行動，還是只保留觀察。
- 在看到工種、地點、需求狀態時，同時知道這些內容是否仍是推測或草稿。
- 若畫面顯示可以出發，也必須知道那只是「出發確認資訊」，不是正式派工或直接救災。

## 這個使用者最怕什麼錯誤

- 把 `推測地點` 當成可前往地址，結果跑錯地方。
- 把 `工種要求` 當成已確認任務分類，直接準備人力或物資。
- 看到 `已確認資料` 或已儲存草稿，就以為可以直接出發，但其實仍需要人工確認。

## 我今天暫時不處理的需求

- 不做真正派工、報到、出勤或導航流程。
- 不做志工媒合、路線安排、現場安全判斷。
- 不串真實 AI API，不做 runtime LLM 判斷。
- 不把任何資料升級成「可以直接行動」的正式狀態。

## 我不採用的 AI 建議

- AI 建議：
  - 把三個 persona 的回饋直接轉成完整 v1 功能清單。
  - 不採用原因：
    - 現在是需求分析階段，應先做取捨；而且功能清單會掩蓋「避免誤導」這個核心風險。
- AI 建議：
  - v1 優先服務資訊整理者，先把資料整理流程做清楚。
  - 不採用原因：
    - 我現在選擇以行動者為主要使用者，因為最需要被降低的風險是「看了畫面後做出錯誤行動」。整理者需求仍重要，但會作為支援行動者判斷的背景能力。

## 必須保留人工確認的判斷

- 這筆資訊是否足以讓行動者採取任何現場行動。
- 推測地點是否足以作為集合或前往依據。
- 工種要求是否符合現場實際需求，或只是系統/草稿推測。
- 資訊是否過期、衝突，或需要先聯絡來源確認。
- 轉述資訊是否取得當事人同意。

## v1 行動狀態規則

目前前端使用四種行動者狀態，接手者修改時請保留「避免誤導成派工」這個原則：

- `先不要出發`：未查核或資料品質不足。現場幫手不出發、不帶物資、不揪人。
- `先確認來源`：資訊來自轉述、電話、社群，或文字含不確定語句。下一步是聯絡來源或值守者，不是去現場處理。
- `可以出發確認資訊`：來源、時間與可核對地點相對清楚，可以派人去核對公告、物資或集合點狀態；仍不是正式派工，也不是直接救災。
- `只作為線索`：資料可用於整理者規劃下一輪查證，但現場幫手暫時不用動作。

## 今天明確不做什麼

- Release 01 階段不修改 `src/`。
- 不新增後端、資料庫、外部 API 或真實 LLM runtime。
- 不把 `needs_review` 或 `unverified` 顯示成已確認。
- 不做實際救災、撤離、派工或路線建議。

## 我仍不確定的地方

- 如果 v1 服務行動者，`工種要求` 是否仍應該放在最高視覺層級，還是要先顯示「目前能不能行動」。
- 是否需要新增比 `不可直接行動` 更白話的行動者狀態，例如「先不要出發」「先確認來源」「只作為線索」。
- 行動者需要看到多少原文與查核理由，才不會只看標籤就行動。
